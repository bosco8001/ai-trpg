## 單一目標與範圍

像把已備份的原稿與確認過的修改單一起交給保管員：寫入前再核對一次，只修改選中的一份資料，並留下可查詢的結果。

新增目前配置角色資料或槽 1、2、3 的單份修復套用、原面板中的再次確認、持久結果查詢與報告下載。只沿用 R02 已確認的活動標記與玩家 MP 相容欄位修復；不補造缺值、不猜角色或資源、不跨來源取證、不呼叫 LLM、不在正常 Load 暗中修復，不提供備份還原、批次套用或刪除。

本稿批准範圍包含必要的來源變動守衛與結果保存結構；PostgreSQL migration 沿用手動執行流程，不在啟動時自動修改資料。一般遊戲操作只接入必要競爭守衛，不改玩法結果、存檔格式或既有敘事規則。

## 準備資格、來源與變動守衛

- 套用綁定已保存且校驗成功的備份、配置角色、儲存模式、固定來源、修復識別碼、格式／規則版本、原稿指紋與候選指紋。前端不能指定任意角色、SQL、路徑、候選內容或修改後數值。
- 增加來源專屬、不能重用的變動標記，獨立於遊戲 revision 與存檔 sourceRevision。所有服務端會寫入該來源的操作須原子更新標記；目前資料包括 gameplay、Load、Reset、已保存敘事及協調紀錄，存檔槽包括 Save 覆寫及本次修復。只有讀取、不寫入的拒絕，不改標記。
- 備份準備必須把同一時刻的完整原稿與變動標記綁定，持久保存後才能取得套用資格。套用同時核對完整指紋與標記，不能只用 revision，也不能只比對修復欄位。來源改動再改回、同值覆寫或刪除後重建，均不能讓舊準備恢復有效。
- PostgreSQL 的標記與來源寫入共用資料庫原子邊界，正常重啟後保留；Memory 的標記綁定目前程序，重啟後不重用。標記缺失、無法核對或版本不支援時拒絕套用，不自行補成有效授權。
- **既有 Phase 31 備份保持原樣，可查詢及下載；未記錄新守衛的舊準備不能套用。** 使用者須以新識別碼重新預覽及保存備份；不改寫舊檔或替舊準備補推測的歷史。
- 守衛涵蓋本服務的寫入。維運若直接改寫、還原資料庫或繞過守衛，須使相關舊準備失效；不宣稱能由最後相同的原稿推回服務外的修改歷史。
- 本輪實作以 PostgreSQL 來源表 trigger 覆蓋一般 SQL INSERT／UPDATE／DELETE（包括同值 UPDATE）；TRUNCATE 輪換全域修復 epoch。整庫還原或關閉 trigger 的維運作業，須停服務，完成後手動輪換 epoch 才重啟；不能宣稱自動辨認還原。操作見 Phase 32 文件。
- 存檔玩家角色必須與配置角色一致。合法舊 Run／其他 world 仍可單獨修復，證據只取自該槽，不依賴目前資料能否讀取；不更換角色／Run／world，也不代表可以 Load。
- 目前資料必須以自身完整原稿通過既有候選驗證，保留原角色、Run、world、戰鬥及敘事身分。沒有來源 lineage 證據時保持受阻，不用其他槽或最新 Settlement 猜測補回。

## 套用的受保護邊界

預覽、備份準備及等待再次確認時可以繼續遊戲。只有實際核對／寫入期間，對所選來源短暫保護，協調既有 gameplay、Save／Load／Reset 與敘事寫入；不長時間鎖住遊戲等待使用者。

同一修復識別碼的消費資格與來源寫入也必須協調，避免兩個分頁或並行請求各套用一次。PostgreSQL 須跨程序協調；Memory 保持單一權威遊戲程序的部署前提，不宣稱多程序共享不同記憶體狀態仍能一致套用。

實際套用依序完成：

1. 驗證請求範圍，取得同識別碼既有狀態；已開始或已完成的同次請求只回傳狀態／結果，不進行第二次寫入。相同識別碼綁定不同內容則拒絕。
2. 校驗持久備份及其準備資格，確認結果保存能力、容量與必要紀錄可用。兩種模式都須先持久取得同識別碼唯一的已開始資格，再嘗試修改來源；只有取得資格的該次處理可執行套用，其他請求只讀取結果。開始資格不能因來源交易回滾而消失，避免後續重複請求再套用；停機後不自動接手未決資格。
3. 在所選來源的受保護邊界內重新讀取完整原稿，核對角色、來源、程序資格、變動標記、格式／規則版本與完整指紋。
4. 由伺服器依同一份原稿重建候選，完整驗證，核對候選指紋及使用者確認的差異。任何不符皆不換成新候選、不自動重試。
5. 加入以下已確認的系統版本效果，再驗證最終整筆資料；只允許有限修復差異及明列的系統 metadata 變動。
6. 單次提交所選來源及結果。不初始化、不借用會暗中 Save／Load／Reset 或正規化原稿的路徑，不寫入部分候選。

核對不通過時，保留備份，回報確定未套用的原因，要求手動重新預覽；已確認的拒絕紀錄也須保存。儲存或斷線故障若無法證實提交結果，使用「結果尚未確認」，不推定已回滾。

## 成功寫入的系統效果

### 目前資料

- 在同一提交中修復有限欄位、revision +1 exactly once、配置新且不重用的 generation、更新來源變動標記。revision 超出安全範圍或無法合法更新時拒絕，不能倒退或重設。
- 保留同一角色／Run／world、已保存 History、敘事識別紀錄、sequence high-water 及 allocator；不重排、重播或補造已保存故事。
- 舊 generation 的未完成 AI 工作遵守 [Phase 26 完整規格](PHASE_26_FINAL_SPEC.md) 第 5 節守衛：回覆丟棄，不保存、不顯示、不發布 fallback。取消網路請求只是優化，不能取代提交時的守衛。
- 未完成敘事可能不再出現，本階段不新增自動重新生成。修復不呼叫 LLM，也不為修復新增故事。
- 已保存敘事若先於修復寫入，會改變來源，舊準備失效；修復若先提交，舊 generation callback 不能再寫入。兩者共用同一競爭邊界。
- 確定未套用時，本次修復不改 revision／generation；其他合法並行操作仍可能修改來源，不能把它們的結果算成本次修復寫入。

### 存檔槽

- 只更新選定槽的有限修復欄位及獨立變動標記。保留原 savedAt 精度、sourceRevision、格式版本及角色／Run／world；修復時間寫入獨立報告。
- 不更新目前遊戲的 revision／generation／History，不呼叫 Load。修復後是否可載入仍依既有 Load 規則判定。
- 其他槽與目前資料保持原樣；相關 Save 若先寫入所選槽，舊準備失效。

## PostgreSQL 與 Memory 故障契約

### PostgreSQL

- 先以獨立持久紀錄取得唯一開始資格，避免來源交易失敗後重複執行。同次資格的完成轉換、來源核對、完整資料修改、變動標記及成功報告在同一資料庫交易完成。任何確定的提交前失敗，不留下部分修復或成功報告；既有開始紀錄仍保留，另保存可證實的拒絕結果。
- 明確拒絕保存完整拒絕報告，來源不寫入。同識別碼再查詢或重複送出只取得該次結果。
- COMMIT 回應遺失或連線中斷，不能單靠客戶端錯誤推定失敗。使用者用原識別碼手動查詢持久結果；查詢也失敗便保持尚未確認，不自動再提交。
- 正常重新啟動後仍可查詢歷次結果。查不到結果不構成撤銷證據，也不能促使系統自動建立新修復。
- 已開始但沒有完成報告的識別碼可永久保持尚未確認，不重新執行、不在重啟後接手。使用者可以手動重新預覽，以新識別碼準備並確認；重新核對來源守衛與完整內容，不能讓舊 ID 再次寫入。這不是判定舊請求失敗或自動復原。

### Memory

- 保持既有遊戲狀態不跨程序持久化的行為。來源替換在同一程序的競爭邊界內整筆完成，與一般操作及 callback 協調，不能留下半份來源。
- 寫入遊戲來源前，先持久保存同識別碼已開始的紀錄及報告容量安排。這一步若確定失敗，不改遊戲來源；不能先改記憶體再嘗試建立去重紀錄。
- 來源替換後保存完整成功報告，或在未替換時保存完整拒絕報告；檔案沿用完整寫入、磁碟同步、原子發布、目錄同步及讀回校驗契約。
- 記憶體替換與磁碟報告不是同一筆跨資源交易。若來源替換後停機或報告保存失敗，不能把它寫成「確定未套用」。同一仍存活程序若保有可信的完成事實，可只補存／取回報告，不再次套用；沒有可信證據則保持尚未確認。
- 重啟後保留已保存的備份、結果與已開始紀錄。舊程序的未決請求永不在新程序續做；歷史成功報告只證明當時完成，不表示目前記憶體仍保有該狀態。
- 不由備份自動恢復遊戲、不以內容相同猜測曾否完成、不把不確定結果改標失敗。重新準備只能基於新程序的目前來源及新的使用者確認，不能自動延續舊請求。

## 結果、報告與取回

- 唯一修復識別碼沿用本次備份準備紀錄，不另造一個套用識別碼。準備完成只表示「備份就緒，尚未套用」，不能當作成功修復。
- 區分備份就緒、請求已開始／尚未確認、確定已套用、確定未套用，以及目前無法讀取／沒有可確認紀錄。回應逾時、關閉面板或查不到紀錄，均不是取消或拒絕的證據。
- 成功與明確拒絕保存完整報告：報告格式版本、識別碼、角色／來源／儲存模式、規則版本、備份校驗關聯、來源及候選指紋／變動標記、準備與結果時間、結果、修復前後差異或固定拒絕原因，以及適用的 revision／generation／槽 metadata 效果。
- 報告不能宣稱未執行的步驟已通過。拒絕報告註明拒絕位置與已完成的核對；無法核對的值保留未知，不補猜測值。無效、未綁定任何合法準備的任意請求不構成完整修復報告。
- 尚未確認的操作保留可持久查詢的進度；不能產生假的成功／拒絕報告。若保存報告本身故障，回應說明目前無法確認或保存結果，不能假稱完整拒絕報告已保存。
- 一般摘要與錯誤不包含完整原稿／故事、SQL、stack、路徑、密碼或連線參數。完整備份仍透過既有下載取回；報告可包含已確認修復欄位值，不複製整段故事。
- 歷次報告與備份全部保留，不自動刪除。查詢、分頁及下載限制在目前配置角色範圍內；來源不再存在、已過期或已套用，都不刪除歷史證據。
- 報告下載使用獨立版本及 SHA-256 校驗封裝，伺服器與前端核對格式、大小及校驗；損壞時拒絕，不提供部分檔案。網頁只宣告已發起下載，不宣稱磁碟已保存。

## 工程容量與逾時提案

沿用第一階段可調整的工程限制；這些不是玩法數值，不新增上限設定 UI。

| 項目 | 處理方式 |
|---|---|
| 單份來源 | 10 MiB UTF-8；超限拒絕，不截斷 |
| 完整備份封裝及下載 | 32 MiB；保留既有上限 |
| 報告封裝及下載 | 本輪採 64 KiB 有界工程值，低於原提案 32 MiB；只含兩個有限差異及 metadata，提交前驗證全份報告並預留 64 KiB，超限不修改來源 |
| 保存總容量 | 預設 1 GiB，合併計入備份、結果及必要紀錄／預留；並行請求不能各自挪用同一餘額 |
| 結果保存容量 | 寫入前確保成功或拒絕報告有容量；達限或保存能力不可用時不開始修改來源，保留既有查詢與下載 |
| 一般 JSON／分頁 | 64 KiB／每頁 20 筆；一般摘要不附原稿 |
| 前端等待 | 套用、手動查詢及下載各整次 30 秒；逾時保留識別碼，不自動重送 |
| PG 操作 | 專用有界連線，取得連線 1 秒、每條查詢 2 秒；不調整一般遊戲連線設定，逾時不保證撤銷提交 |

若故障使完整拒絕報告也無法持久保存，來源保持確定未改時可以說明本次未進行來源寫入，但不得聲稱已存在持久拒絕結果；介面仍保留識別碼及保存失敗提示供手動查詢。若連先前結果都不能讀取，不能宣稱未套用。

### 狀態與拒絕邊界

| 情況 | 持久紀錄／對原 ID 的效果 | 後續操作 |
|---|---|---|
| 任意無效格式、未綁定準備、角色範圍不符 | 不建立開始紀錄、不修改任何既有 ID；沒有完整修復報告 | 修正請求或手動重新預覽準備 |
| 同 ID 內容衝突 | 不覆寫、不消費原請求；原紀錄保持原狀 | 查詢原 ID |
| 舊備份無守衛、舊 Memory 程序或 epoch 失效 | 備份保留，資格不成立；不開始、不產生假套用／拒絕報告 | 新識別碼重新準備 |
| 開始前容量不足／保存能力不可用 | 本次不寫來源；無完整報告保存保證；若先前結果也無法讀取，保持無法確認 | 保留 ID 手動查詢；介面不自動重送 |
| 已持久開始後核對來源／候選不通過 | 保存完整拒絕報告；本次不寫來源；ID 已消費 | 新識別碼重新預覽準備 |
| 已持久開始後發生儲存、斷線或逾時故障 | ID 已消費，不能再套用；沒有可信完成證據則保持尚未確認 | 手動查詢；需要時新識別碼重新準備 |
| 已確認套用或拒絕 | 終態報告不可覆寫；相同請求只讀回結果 | 查詢／下載 |

## 原面板再次確認與結果呈現
