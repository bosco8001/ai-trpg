# R03 第一階段：持久備份與修復準備確認稿

整理日期：2026-10-01；批准日期：2026-10-02；驗收日期：2026-10-03（Asia/Hong_Kong）。使用者原文：「A，同意實作，實作後幫我push」。**本稿完整範圍作為 Phase 31 已交付，使用者其後明確回覆「Phase 31通過」；驗收與工程來源見 [交付紀錄](PHASE_31_REPAIR_PREPARATION.md)。** 本稿依 [R03 十項已選條件](R03_REPAIR_APPLY_DISCUSSION.md) 整理，不新增玩法 Canon。本稿當時不批准套用；第二階段其後於 2026-10-04 另行批准，見 [第二階段完整契約](R03_SECOND_STAGE_PROPOSAL.md)，待文件工程審查後實作，沒有延伸本稿的 commit／push 授權。

## 單一目標與邊界

像先把待修原稿放進可取回的保管箱：從 R02 預覽選一份來源，保存完整原稿與修復準備紀錄，再提供查詢及下載。介面明示「備份就緒，尚未套用」。本階段沒有套用、還原或刪除入口。

只新增備份與準備紀錄的持久寫入；不改目前遊戲資料、三個存檔槽、保存時間、版本／generation、敘事或資源，不呼叫初始化、hydrate、Save、Load、Reset 或 LLM。PostgreSQL 的新 migration 只新增備份所需結構，沿用手動 migration 流程，不在伺服器啟動時自動建立資料。

第二階段的原子套用、再次確認與完成報告，須等本階段經 Grok Bot 驗證並由使用者接受後，另行確認完整寫入契約才實作。

## 來源與準備條件

- 固定來源為配置角色的目前資料及槽 1、2、3，每次只選一份，不接受請求指定角色、資料庫、路徑或任意修復內容。
- 沿用 [Phase 30 規格](PHASE_30_REPAIR_PREVIEW_SPEC.md) 的兩種有限修復候選。伺服器重新讀取原稿，核對來源及候選指紋、格式／規則版本，重新建立並整筆驗證候選；不信任前端提供的差異作為修復證據。
- 原稿已變動、候選受阻、沒有待修差異、資料不存在、空槽、版本不支援或超限時，拒絕建立就緒紀錄，要求手動重新預覽；不自動換成新候選。
- 存檔玩家角色必須與配置角色相同。相同角色的舊 Run／其他 world 可以準備，但必須自身完整合法，證據只取自該槽；不要求目前資料讀取成功，不改身分或轉換世界。
- 可以繼續遊戲。備份代表擷取時刻，完成後不保證仍是最新來源；介面顯示時間及已知的過期狀態，不承諾即時察覺其他分頁的變動。未來套用仍須重新核對來源。

## 持久保存與完整性

- PostgreSQL 保存至新的備份紀錄表，完整原稿以文字保存，不能經 JavaScript 數字轉換或改存 JSONB 而失去來源表示。Memory 保存至伺服器專用本機目錄，目錄不納入 Git，路徑由伺服器設定。
- 完整保留所選來源的原始文字及來源資訊，包括已保存故事、敘事識別、協調資訊與存檔時間精度。資料庫備份保留目前資料庫的表示，不宣稱找回最初寫入前的排版。
- 使用獨立版本的單一 JSON 備份封裝，含修復識別碼、配置角色、來源／儲存模式、擷取時間、來源及候選指紋、規則版本、差異與完整原稿。固定校驗資料的編碼，附 SHA-256，校驗值本身不參與計算；實作交付須附可供 Grok 獨立重算的格式說明。
- PG 以交易完整保存備份與必要紀錄。Memory 以不可覆寫的完整檔案、同步磁碟、原子發布及目錄同步保存，防止同一識別碼被並行覆寫。不支援所需持久保存能力、權限不足或任何保存／校驗失敗，都不能顯示就緒。
- 只有完整保存並讀回驗證內容與校驗成功，才回報「備份就緒」。不完整檔案不能被當作有效紀錄；錯誤不洩露故事、SQL、路徑或連線資訊。
- 兩種模式重啟後仍可查詢及下載已保存備份。Memory 的遊戲狀態仍遵守原本的生命週期；保留備份不代表遊戲狀態持久化。舊程序的準備紀錄不構成新程序的套用授權，未來必須重新預覽及準備。

## 識別碼、回應遺失與取回

- 前端送出前產生唯一修復識別碼，綁定固定來源、角色範圍、指紋與版本。同一識別碼、相同內容的重複請求只取得同次紀錄，不建立第二份；內容不同則拒絕，並行請求也遵守此規則。
- 逾時、斷線、取消等待或離開面板，不代表伺服器已撤銷保存。介面保留識別碼，讓使用者手動查詢結果，不自動重送準備請求、不自動開始新修復。
- 查不到紀錄或讀取失敗時，清楚區分「目前沒有可確認的紀錄」與「目前無法讀取」；都不能冒稱保存成功、撤銷成功或已套用。重啟後也遵守相同語義。
- 可列出配置角色的歷次備份摘要，分頁每頁 20 筆；一般摘要與錯誤不含完整故事。可依識別碼下載完整備份，伺服器與前端都核對格式、大小及校驗後才發起下載；損壞時拒絕，不提供部分檔案。
- 已保存備份全部保留，過期或取消等待不刪除；本階段不自動清理、不新增刪除或還原 API。網頁只提示已發起下載，不能宣稱已確認使用者磁碟寫入。

## 已批准工程上限

這些是可調整的伺服器工程設定，不是玩法 Canon，也不新增使用者自訂上限 UI。

| 項目 | 上限 |
|---|---|
| 單份來源 | 沿用 R02 的 10 MiB UTF-8 上限 |
| 完整備份封裝／下載 | 32 MiB，包含外層與原稿字串編碼；超限拒絕，不截斷故事 |
| 備份總容量 | 每個保存位置預設 1 GiB；包含完整備份與必要紀錄，並行保存須一併計入。達上限拒絕新增，不刪舊備份，既有查詢／下載仍可用 |
| 一般 JSON 回應 | 64 KiB；摘要分頁不附原稿 |
| 前端等待 | 準備、查詢及完整下載各共用一次 30 秒上限；只收到標頭不能解除限制 |
| PG 操作 | 取得連線 1 秒、每條查詢 2 秒，使用專用且有界的備份操作連線；不調整一般遊戲連線設定。釋放連線不宣稱查詢立刻停止 |

## 介面與驗收交付

正常系統面板與初始讀取失敗畫面都可進入。從有效候選選「保存修復前備份」，顯示來源、前後差異、識別碼、時間與備份狀態，再提供手動查詢及下載。沒有套用按鈕；防重複觸發、防舊回應覆蓋，等待／成功／失敗不搶鍵盤焦點。

開發代理可準備測試與隔離樣本，但不執行任何測試或工程驗證。交付須列出變更檔案、待 Grok 驗證狀態、限定本次檔案的 commit／push 指令、取得完整 SHA 的命令，以及完整 Grok Bot 審查 prompt。

Grok 驗證重點：兩種儲存模式的重啟取回；保存前後遊戲來源完全不變；來源變動與角色不符拒絕；同長度改字及配置角色影響指紋；原稿數值／時間精度；同識別碼並行與內容衝突；容量／磁碟／權限／交易故障；讀回校驗與損壞檔案；回應遺失／逾時／取消；查詢與下載範圍；前端舊回應與重複觸發；Phase 26–30 回歸。Grok 的工程報告不代替使用者的最終接受。

使用者可手動確認：每次只備份一份、遊戲仍能操作、顯示「尚未套用」、取消後可查詢、重啟後可下載，以及手機上的按鈕與提示。完成後停在本階段，不開始原子套用。
